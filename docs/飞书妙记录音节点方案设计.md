# 飞书妙记录音节点 · 方案设计

> 版本 v0.1 ｜ 2026-10-14 ｜ 状态：**待评审**
> 关联文档：《全流程说明.md》§2.2 到店直招、《语音识别ASR成本评估.md》
> 决策基调：**用飞书妙记完成「到店直招录音 → 自动转文字 → AI 参考评分」闭环**（用户已拍板）

---

## 0. 结论先行

1. **核心机制**：到店直招建档时生成 6 位短码 `walk_in_code`，店长面试时打开飞书妙记录音、**把妙记标题填成短码**；后端定时轮询飞书妙记（按店长 + 时间窗搜索），命中短码后拉取逐字稿，交给新增的「整场面试整体评分」能力产出 **AI 参考分**，与店长人工打分并存。
2. **三个待验证假设（POC 先行，见 §12）**：① bot 能否读到店长的私有妙记；② 短码写在标题里能否被 search 原样取回并可靠匹配；③ 昆明话/门店噪音下妙记转写质量。
3. **不覆盖**：本方案不改线上 AI 面试链路，只补「到店直招」分支；录音存档、人工打分能力保持不变。

---

## 1. 背景与目标

### 1.1 现状

- 到店直招：店长现场面试，一次建档（姓名/手机/来源渠道），可上传**整场面试录音**（`offline_interviews.audio_*`），但**录音仅存档**，打分靠店长人工录入（`POST /admin/offline-interviews/{id}/score`）。
- 语音转文字（ASR）原定「阶段 B」走云 ASR API；现改为用**飞书妙记**承担转写（团队已重度使用飞书，店长零新工具成本）。

### 1.2 目标

让店长**打开飞书妙记 → 录音 → 结束**即可，其余（转写、关联、评分）由系统自动完成，减少店长人工打分负担，并沉淀逐字稿供 HR 复核。

### 1.3 非目标

- 不做实时转写（妙记本身异步，接受分钟级延迟）。
- 不替代店长人工打分，只产出「AI 参考分」供店长确认/覆盖。

## 3. 总体链路

```mermaid
flowchart LR
    A[店长后台建档<br/>领短码 8231] --> B[打开飞书妙记<br/>标题填 8231 录音]
    B --> C[妙记转写完成<br/>自动生成逐字稿]
    C -.定时轮询.-> D[search 店长+时间窗]
    D --> E[短码正则匹配<br/>命中 offline_interviews]
    E --> F[detail 拉逐字稿]
    F --> G[整场面试整体评分<br/>AI 参考分]
    G --> H[落库 + 可选推 HR]
```

- **人操作**：A（建档，已有）、B（店长开妙记填标题录音）。
- **系统自动**：C 之后全部（轮询、匹配、拉取、评分、落库）。

## 4. 关键设计决策

### D1 · 短码关联（已定：标题填短码）

- 建档时生成 6 位数字短码 `walk_in_code`，唯一索引（冲突重试）。
- 店长把妙记**标题**填成短码（前端在建档结果页大字展示 + 一键复制 + 提示语）。
- 后端匹配时用正则 `\b\d{6}\b` 从 search 返回的 `title` 中提取，反查 `offline_interviews.walk_in_code`。
- 兜底：若标题未命中，可再用「店长 open_id + 面试预约时间 ± 30 分钟」的弱匹配给出候选，供后台人工确认（不自动绑定）。

### D2 · 身份与可见性（POC 定）

- **首选**：后端用 bot 身份（`minutes:minutes.search:read` scope）+ `tenant_access_token` 调 search / detail。复用现有 `get_tenant_access_token`。
- **兜底**：若 bot 读不到店长私有妙记，改用**店长本人 user_access_token**（飞书 OAuth，`refresh_token` 长期续期）拉取。代价是引入 token 刷新与「每店长一份授权」的运维负担。
- 两者共用同一层抽象（`fetch_minutes(owner_open_id, start, end)` → `list[MinuteItem]`），后端只认结果，不感知身份差异。

### D3 · 评分语义（新增「整场整体评分」）

- 店长录音是**双向自由对话**，不是逐题回答，**不能复用逐题 `evaluate`**。
- 新增 `score_whole_interview(transcript, jd, rubric) -> {scores, comment, verdict}`：把整场逐字稿 + JD + rubric 一次性喂 LLM，按维度给分 + 总体评价 + 录用建议。
- 与现有 `evaluate` 完全同构：纯文本 JSON 输出 + 手动解析 + 降级兜底（`_parse_json_response` / `_coerce_answer_score` 可复用思路）。
- 产出写入 `ai_score / ai_dim_scores / ai_comment`，**不覆盖**店长人工 `score`，作为「AI 参考分」在前端并列展示，店长可一键采纳或改分。

### D4 · 店长 open_id 映射（关键缺口）

- 轮询需要按「店长 open_id」过滤，但库里只有店长姓名。
- **推荐**：建档/约面时由 HR 填店长姓名/手机，后端用飞书通讯录 API（`contact/v3/users` 按手机号/邮箱查询）解析 open_id 存 `interviewer_open_id`。
- 解析失败降级：店长在后台「线下复试」页手动粘贴妙记链接（`minutes_url` 解析出 `minute_token`），跳过轮询直接绑定。
- POC 需验证：通讯录按手机号解析 open_id 的可用性与权限。

## 5. 数据模型改动（Alembic `0008_feishu_minutes`）

在 `offline_interviews` 新增：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `walk_in_code` | String(16) | NULL，唯一索引 | 建档生成的短码 |
| `interviewer_open_id` | String(64) | NULL | 店长飞书 open_id（通讯录解析） |
| `minutes_token` | String(64) | NULL | 妙记 token（`/minutes/<token>`） |
| `minutes_url` | String(512) | NULL | 妙记链接（回查/展示） |
| `minutes_title` | String(255) | '' | 妙记标题快照 |
| `transcript_text` | Text | NULL | 逐字稿全文 |
| `transcript_status` | String(32) | 'none' | 见状态机 |
| `transcript_at` | DateTime(tz) | NULL | 转写落库时间 |
| `ai_score` | Float | NULL | AI 参考总分 |
| `ai_dim_scores` | JSONB | [] | AI 维度分 |
| `ai_comment` | Text | '' | AI 总体评价 |
| `ai_scored_at` | DateTime(tz) | NULL | AI 评分时间 |

**`transcript_status` 状态机**：

```
none ──建档生成短码──► pending ──轮询命中妙记──► matched ──拉取逐字稿成功──► transcribed
                              │                      │
                              └──────────────────────┴──► failed（记录原因，可重试）
```

- 存量记录默认 `none`（无短码，不受轮询影响）。
- `matched` 之后拉逐字稿成功即 `transcribed` 并触发评分；拉取/评分失败置 `failed` 并记录原因，轮询可重试。

## 6. 飞书对接设计

新增 `app/services/feishu_minutes.py`，复用 `feishu_notify.get_tenant_access_token` 与 `_api_get` 的传输模式：

```text
search_minutes(owner_open_id, start, end, page_token)   # POST /open-apis/minutes/v1/minutes/search
get_transcript(minute_token)                            # 逐字稿接口（POC 用 lark-cli --dry-run 确认精确路径）
```

- **search**：`owner_ids=[店长 open_id]` + 时间窗（`start` 为上次轮询水位，`end` 为 now），分页取全。
- **匹配**：对每条 `item.title` 做 `\b\d{6}\b` 提取 → 反查 `walk_in_code` → 命中且未绑定则绑定 `minutes_token/title`，置 `matched`。
- **拉取**：`get_transcript` 得到逐字稿 → 存 `transcript_text`，置 `transcribed` → 触发 `score_whole_interview`。
- **身份抽象**：`MinutesClient` 接口，bot / user 两种实现，配置开关切换。

> 精确 Open API 路径与返回结构，POC 阶段以 `lark-cli minutes +search --dry-run` / `minutes +detail --transcript --dry-run` 为准，文档不臆造。

## 7. 轮询任务设计

- **载体**：`main.py` lifespan 启动一个 `asyncio` 后台任务（`asyncio.create_task`），关闭时取消。不引入 APScheduler 等新依赖。
- **开关**：`FEISHU_MINUTES_POLL_ENABLED`（默认 false，POC 通过后再开）。
- **周期**：`FEISHU_MINUTES_POLL_INTERVAL`（默认 180s，可配 60~600）。
- **单次执行**：
  1. 查 `transcript_status in (pending, matched, failed)` 且 `interviewer_open_id` 非空的记录；
  2. 按店长 open_id 分组，逐店长 `search_minutes`（时间窗 = 最近 7 天，覆盖补录）；
  3. 短码匹配 → 绑定 → 拉取 → 评分（见 §8）；
  4. 记录每店长的处理水位（内存/库，避免重复翻页）。
- **幂等**：绑定与落库以 `walk_in_code` / `minutes_token` 唯一约束 + `transcript_status` 状态机保证，重复轮询不产生副作用。
- **隔离**：任何一步失败只记日志并置 `failed`，**绝不影响主流程**（与现有 feishu_notify 同策略）。

## 8. 评分接入设计

- 新增 `app/services/whole_interview_scoring.py`（或作为 `scoring.py` 的扩展）：
  - 输入：`transcript_text`、`job.jd_text`、`interview_templates.rubric`。
  - prompt：复用 `evaluate.py::SCORING_SYSTEM_PROMPT` 的评分基准/锚点/校准思想，但把「当前问题 + 回答」换成「整场逐字稿」，输出一次性维度分 + comment + verdict。
  - 解析：复用 `_parse_json_response` / `_coerce_answer_score` 的容错套路。
- 结果写 `ai_score / ai_dim_scores / ai_comment / ai_scored_at`，`transcript_status` 保持 `transcribed`。
- **人工优先**：前端「线下复试」页并列展示「AI 参考分」与「人工分」，店长可「采纳 AI 分」一键回填到 `score/dim_scores/comment`，或直接手改。
- 可选（阶段二）：`ai_score` 生成后按阈值推送 HR 复核（复用 `feishu_notify`）。

## 11. 合规与降级

- **知情同意**：沿用现有《安全知情协议》思路——到店直招建档页增加「录音转文字用于评估」告知与勾选（`transcript_status != none` 的前提）。候选人录音与逐字稿均属个人信息，需明确留存期限。
- **数据落位**：逐字稿与妙记链接存 `offline_interviews`，随现有删除/级联清理（`cascade.py`）一并处理；妙记原文件保留在飞书侧，由店长自行决定留存。
- **降级链**：短码未命中 → 弱匹配候选人工确认；bot 不可见 → 切 user 身份；转写失败 → `failed` 可重试；评分失败 → 仅记录、不阻断转写落库。

## 12. POC 验证清单（先做，未通过不进入编码）

| # | 假设 | 验证方法 | 通过标准 |
|---|---|---|---|
| H1 | bot 能读到店长私有妙记 | 拿一条真实店长妙记，`lark-cli minutes +search --as bot --owner-ids <店长open_id>` + `minutes +detail --as bot --transcript` | search 返回该妙记且 detail 能拿到逐字稿 |
| H2 | 标题短码可可靠匹配 | 妙记标题填入 `8231`，search 返回的 `title` 字段是否原样含 `8231`（`--format json` 看字段） | title 原样可读、正则命中 |
| H3 | 转写质量达标 | 拿 1~2 场真实面试录音（含昆明话/门店噪音）上传妙记，人工比对逐字稿 | 关键问答可辨识，误识别不致命 |
| H4 | 通讯录解析 open_id | 按店长手机号调 `contact/v3/users/batch_get_id` 或 `find_by_department` 实测 | 能解析到店长 `ou_` open_id |

> 执行顺序：H1/H2/H3 用 lark-cli 一天内可跑完；H4 并行验证。任一失败即回退到 §4 的兜底方案（user 身份 / 手动绑定 / 云 ASR），不强行推进。

## 14. 风险与开放问题

| 风险/问题 | 影响 | 应对 |
|---|---|---|
| 店长妙记归属个人、bot 读不到 | 链路断裂 | POC H1 先行；兜底 user token / 手动绑定 |
| 店长不愿/忘记改标题填短码 | 匹配失败 | 建档页强提示 + 兜底弱匹配 + 手动绑定通道 |
| 同店长密集面试，短码串场 | 误关联 | 短码唯一 + 时间窗 + 面试预约时间辅助，绝不自动绑定弱匹配 |
| 整场评分无逐题粒度、可能偏粗 | AI 参考分可信度 | 定位为「参考分」，店长人工确认/采纳，不自动决策 |
| 妙记 ASR 额度（免费 300 分钟/月/人） | 转写中断 | 监控 `quota_exceeded`，提示升级或切换云 ASR 兜底 |
| 妙记无事件推送、轮询延迟 | 分钟级延迟 | 面试评分非实时场景，可接受；周期可调小 |
| 转写文本口径（口语冗余/方言） | 评分失真 | 复用现有「口语转书面语」清洗思路，评分前轻量规整 |
